# Prototype Checkpoints and Promotion

The Human invokes `$prototype-engineer` directly for rapid prototype work. The
PM does not supervise each edit, restore context for the engineer, or require a
Work Package, Ledger update, documentation change, or handoff for the rapid
loop.

## PM responsibility

Use this reference only when the Human asks the PM to checkpoint, approve,
lock, document, or promote prototype behavior.

At that boundary:

1. inspect the selected prototype state and relevant approved constraints;
2. identify which findings are experiments and which are proposed durable
   product decisions;
3. ask the Human only for consequential unresolved decisions;
4. record approved behavior as Canonical Truth when useful;
5. capture a concise source-to-target promotion map if production work follows.

Do not reconstruct the full history of rapid edits. The selected checkpoint is
the evidence that matters.

## Promotion boundary

A prototype remains non-authoritative until the Human approves a checkpoint.
Promotion should preserve approved navigation, behavior, content, and visual
decisions while replacing local seed adapters with production integrations.

The Human invokes `$full-stack-engineer` directly for promotion or production
implementation. Define a Work Package only when the production change benefits
from durable scope, acceptance, dependencies, or release requirements.
